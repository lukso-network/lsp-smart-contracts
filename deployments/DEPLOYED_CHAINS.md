> See also: [README.md](./README.md) for instructions on how to deploy these contracts on new EVM chains.
> The list of chains is also available in the JSON file [`chains-mainnet.json`](./chains-mainnet.json) for easier parsing.

This file is the per-contract address registry for Universal Profile base contracts across supported EVM chains.
Deployments use deterministic CREATE2, so each contract version resolves to the same address on every chain where it is deployed.

## Networks

> **Notes for the following zk networks ⚡️: zkSync, Immutable zkEVM, and Lens**
>
> On these networks, the Universal Profile / Token implementation contracts were deployed as **standard EVM bytecode** and run via the chain's **EVM bytecode emulator/interpreter** (not as native EraVM / zkEVM bytecode compiled with `zksolc`).
>
> **Integrators and developers must take this into account**, for proxies deployed calling these implementations via `delegatecall`:
>
> - ✅ a `zksolc`-compiled (native) proxy **cannot** `delegatecall` into an EVM-emulated implementation
> - ❌ an EVM-emulated proxy **cannot** `delegatecall` into a `zksolc`-compiled implementation
>
> **What to do:** compile and deploy your proxies (and any clone/factory that creates them) with standard **`solc`** ✅ so they stay in the same EVM-emulated environment as the Universal Profile / Token implementation contracts.
> Do **not** point a `zksolc` ❌ proxy at these implementation addresses — calls will revert.
>
> Regular `call` / `staticcall` between EVM-emulated and native contracts still works; only `delegatecall` (proxies / libraries) is blocked across the VM boundary.
